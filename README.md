# Codenzo — демо CI/CD

Мини-приложение (лендинг с фильтром репетиторов по языку программирования) для тестового задания Junior DevOps.
Стек: Vite + Vanilla JS, тесты — Vitest, линтер — ESLint, CI — GitHub Actions, хостинг — Vercel.

**Деплой:** https://codenzo-demo.vercel.app

## Как устроен пайплайн

Файл: [.github/workflows/ci-cd.yml](.github/workflows/ci-cd.yml). Два job'а:

**`test`** — запускается на каждый push в `main` и на каждый pull request:
1. `npm ci` — ставит зависимости строго по `package-lock.json`, чтобы сборка в CI была воспроизводимой (в отличие от `npm install`).
2. `npm run lint` — ловит ошибки и мусор в коде до запуска чего-либо.
3. `npm test` — юнит-тесты логики фильтрации.
4. `npm run build` — проверяет, что проект вообще собирается.

**`deploy`** — запускается только при push в `main` и только если `test` прошёл (`needs: test`):
1. `vercel pull` — подтягивает настройки проекта с Vercel.
2. `vercel build --prod` — собирает проект.
3. `vercel deploy --prebuilt --prod` — выкладывает уже собранный результат.

Поэтому в PR код только проверяется, а на продакшн попадает только то, что прошло проверки в `main`.

Мелочи: `concurrency` отменяет устаревшие запуски на той же ветке, `cache: npm` ускоряет установку зависимостей.

### Почему такие инструменты
- **GitHub Actions** — код уже на GitHub, ничего дополнительного поднимать не нужно, бесплатно для публичных репозиториев.
- **Vercel** — managed-хостинг без серверов, ровно то, что нужно проекту на раннем этапе.
- **Деплой через Vercel CLI, а не встроенную Git-интеграцию** — чтобы деплой был реально завязан на результат тестов. Иначе Vercel выкатывал бы каждый коммит независимо от CI.

### Секреты (Settings → Secrets and variables → Actions)
| Секрет | Откуда взять |
|---|---|
| `VERCEL_TOKEN` | vercel.com/account/tokens |
| `VERCEL_ORG_ID`, `VERCEL_PROJECT_ID` | поля `orgId` и `projectId` в `.vercel/project.json` после `vercel link` |

## Мониторинг доступности (описание подхода)

Принцип: начать с простого и бесплатного, усложнять по мере роста.

1. **UptimeRobot** (бесплатный план: 50 мониторов, проверка раз в 5 минут) — HTTP-проверка главной страницы и, когда появится бэкенд, отдельного `/health` эндпоинта. Алерты — в Telegram/email. Это закрывает вопрос «сайт вообще открывается?».
2. **Keyword-проверка** — UptimeRobot ищет на странице ожидаемый текст (например, «Codenzo»), чтобы поймать случай, когда сайт отвечает 200, но показывает пустую или сломанную страницу.
3. **Sentry** (бесплатный план) — ловит ошибки JavaScript у реальных пользователей, которые проверка доступности не увидит.
4. **Проверка после деплоя** — в конец `deploy` можно добавить `curl --fail` на задеплоенный URL, чтобы пайплайн краснел, если выкатилось что-то нерабочее.
5. Позже, при подключении Supabase: отдельный монитор на эндпоинт, который делает простой запрос в базу, — чтобы отслеживать и её доступность.

Чего пока не делаем: Prometheus/Grafana, свои дашборды — для раннего этапа это лишняя сложность.

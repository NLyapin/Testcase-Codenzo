# Codenzo, демо CI/CD

Это тестовое задание на позицию Junior DevOps. Приложение сознательно сделано простым: страница со списком репетиторов, который можно отфильтровать по языку программирования. Написано на Vite и обычном JavaScript, тесты на Vitest, линтер ESLint. Главное здесь пайплайн, а не само приложение.

Сайт: https://codenzo-demo.vercel.app

## Как устроен пайплайн

Конфиг лежит в .github/workflows/ci-cd.yml. В нём две задачи.

Первая называется test и запускается на каждый push в main и на каждый pull request. Сначала ставятся зависимости через npm ci. Я взял его вместо npm install, потому что он ставит ровно то, что записано в package-lock.json, и сборка в CI не отличается от локальной. Потом идёт линтер, чтобы отсеять очевидные ошибки до всего остального. Потом тесты, они проверяют логику фильтрации. В конце сборка, чтобы убедиться, что проект вообще собирается.

Вторая задача называется deploy. Она запускается только при push в main и только если test прошёл (за это отвечает needs: test). Она подтягивает настройки проекта с Vercel, собирает проект и выкладывает готовый результат в продакшн. Получается, что в pull request код только проверяется, а на сайт попадает лишь то, что прошло все проверки.

Ещё две мелочи. Блок concurrency отменяет устаревшие запуски на той же ветке, чтобы они не копились. А кеш npm ускоряет установку зависимостей.

## Почему такие инструменты

GitHub Actions потому, что код и так лежит на GitHub, ничего отдельно поднимать не надо, а для публичных репозиториев это бесплатно.

Vercel потому, что это managed-хостинг: не нужны ни серверы, ни администрирование, а проекту на раннем этапе это и нужно.

Деплой я делаю через Vercel CLI из GitHub Actions, а не через встроенную интеграцию Vercel с гитхабом. Причина в том, что встроенная интеграция выкатывает каждый коммит сама по себе, не глядя на результат тестов. Через CLI деплой жёстко привязан к зелёному test.

Для работы нужны три секрета в настройках репозитория: VERCEL_TOKEN (создаётся в аккаунте Vercel), а также VERCEL_ORG_ID и VERCEL_PROJECT_ID (их выдаёт vercel link в файле .vercel/project.json).

## Как бы я настроил мониторинг

Я бы взял за основу один инструмент, Sentry, чтобы не заводить отдельные сервисы под каждую задачу. Начать можно с бесплатного плана и усложнять только по мере роста.

Первое, что нужно знать про сайт, это отвечает ли он вообще. Для этого в Sentry есть Uptime Monitoring: он периодически ходит на главную страницу, а когда появится бэкенд, ещё и на отдельный адрес /health. Если сайт не отвечает или отвечает ошибкой, приходит уведомление в Telegram, Slack или на почту. Так о падении узнаешь раньше пользователей.

Второе, это ошибки у реальных пользователей. Сайт может отвечать 200 и при этом не работать, например из-за ошибки в JavaScript. Для этого в приложение подключается Sentry SDK, и каждая ошибка приходит с описанием, браузером и местом в коде. Если при сборке загружать source maps, в отчёте будет виден исходный код, а не минифицированный.

Третье, это связь с деплоями. Sentry умеет принимать информацию о релизах, и если отправлять её из задачи deploy, то видно, какой именно выкат принёс новую ошибку. Это удобно, когда надо быстро понять, что откатывать.

Что ещё можно добавить, когда проект подрастёт:

Проверка после деплоя. В конец задачи deploy добавить curl --fail на только что выложенный адрес, чтобы пайплайн становился красным, если выкатилось что-то нерабочее.

Мониторинг базы. Когда подключат Supabase, завести эндпоинт /health, который делает простой запрос в базу, и поставить на него проверку. Тогда будет видно и доступность базы.

Срок действия SSL-сертификата и домена. Банальная причина падения сайта это просроченный сертификат или домен, поэтому стоит получать предупреждение за 2-3 недели до окончания.

Скорость загрузки. Если включить в Sentry трассировку, можно следить за временем загрузки страниц. Для сайта, куда заходят родители с телефонов, это важно не меньше, чем доступность.

Статус-страница. Простая публичная страница, где видно, работает ли сервис. Пока у проекта мало пользователей, она не нужна, но когда они появятся, это экономит время на ответах в поддержку.

Дежурства и порядок реакции. Даже для маленькой команды полезно заранее договориться, кто получает уведомления ночью и что считать срочным, иначе мониторинг превращается в шум, который все игнорируют.

Prometheus, Grafana и собственные дашборды я пока не предлагаю. На этом этапе проекта они только добавят сложности.
